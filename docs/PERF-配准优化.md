# 配准优化：231 ms → 9 ms（并行 + 提前终止）

日期：2026-10-22　性质：**零行为变化**的性能优化（逐位等价，四集 + 官方集已验证）

---

## 一、问题：88.7% 的时间不在算法里

用 `DPCB_PROFILE=1` 对 100 对做阶段计时：

| 阶段 | 每对 ms | 占比 |
|---|---|---|
| **配准（`>1b_align` 230.9）** | **231.0** | **88.7%** |
| 负极性闸门 | 22.1 | 8.5% |
| 差分 | 3.5 | 1.3% |
| 分型 + 置信度 | 1.8 | 0.7% |
| 正极性闸门 | 1.5 | 0.6% |
| 区域生长 | 0.6 | 0.2% |
| **合计** | **260.4** | 100% |

`>1a_compact`（两次全图拷贝）只有 0.001 ms，所以 230.9 ms 全在
`TileShiftRegistration.AlignCore`：

```
8 块 × (2×8+1)² = 289 个位移 × 每块 6,400 像素 = 1,480 万次二值 XOR
```

纯 C# 循环、无向量化、无提前退出、8 块串行。

---

## 二、两个手段，都不改算法

### 1. 块间并行

8 个 tile 完全独立：各算各的 `(bdx, bdy)`，各写各的 `aligned[y0..y1, x0..x1)`，
各写各的 `shiftArr[ti]`。**没有共享写，没有读取顺序依赖**，所以 `Parallel.For` 后结果逐位相同。

`tiles < 2`（单块）时退回串行，避免线程池开销。

### 2. XOR 提前终止

```csharp
if (++n > limit) return n;   // limit = 当前最优 best
```

因为更新条件是 `v < best || (v == best && 距离更近)`：

- `n > best` → 不可能更新，提前退出安全；
- `n == best` → 仍可能因距离更近而更新，所以必须算完。

因此 `limit = best` 时**选择结果与全量计算完全一致**。

## 五、还剩多少空间

- 配准 9.0 ms 里仍以 XOR 为主，`Vector<byte>` 向量化理论上还能再 3~5×（约 2~3 ms）；
- 负极性闸门 22.1 ms 已成为新的第一大头，下一轮若要继续压节拍，应看它内部的 Halcon 调用分布；
- 检测器外仍有约 250 ms/对（两张 640×640 JPEG 解码 + 评测匹配 + 文件 IO），压节拍必须一并处理。
